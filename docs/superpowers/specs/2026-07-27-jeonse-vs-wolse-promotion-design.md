# 전세 vs 월세 비용차 비교 — 메인 승격 설계

- 작성일: 2026-07-27
- 상태: 사용자 검토 대기 (개발 착수 전)
- 브랜치: `feat/market-trends-backend`

## 1. 왜 이 문서가 필요한가

원래 제품 질문은 하나였다.

> **"전세 혜택(정책대출·저금리)을 받고 전세로 들어가는 것과 월세로 들어가는 것, 어느 쪽이 얼마나 싼가?"**

지금 배포된 제품에서 이 질문의 답이 놓인 위치는 다음과 같다.

| 계층 | 현재 위치 |
|---|---|
| 브랜드 카피 | "이 집, 주변 시세는 어떻게 흘러왔나" — 시세 조회 앱으로 자기소개 |
| 탭 | 3개 중 3번째 (`내 조건 진단`) |
| 폼 | 그 탭 안 4개 섹션 중 3번째 (`전세 vs 월세 비교 (선택·혜택 반영)`) |
| 결과 | 3개 카드 중 3번째 |
| 기본 동작 | **답이 아예 안 나온다** |

마지막 줄이 핵심이다. [Decision.jsx:45](../../../web/src/Decision.jsx#L45)의 초기값이 `jz: null, wsRent: null`이고, [decision.py:130](../../../src/onjeon/decision.py#L130)이 `if jz and ws_rent:`로 게이트한다. 사용자가 이미 채운 보증금·월세와 **중복되는 3개 필드를 추가로** 채우지 않으면 `jeonse_vs_wolse` 키가 응답에 없다. 즉 기본 흐름을 그대로 따라가면 제품의 원래 질문에는 답하지 않는다.

승격은 UI 재배치가 아니다. 네 가지가 동시에 바뀐다.

1. **진입점** — 첫 화면에서 두 안을 입력하고 한 문장으로 답한다
2. **숫자의 정직성** — 지금 숫자는 헤드라인으로 쓰기에 결함이 5개 있다 (§2)
3. **리스크 조정 복원** — 제안서의 유일한 차별점이 배포 경로에서 꺼져 있다 (§2 결함 D)
4. **근거 노출** — 왜 그 숫자인지 항목별 분해 + 조항 인용

## 2. 지금 숫자의 결함

승격하면 이 숫자가 화면 제일 위 큰 글씨가 된다. 그 전에 고쳐야 하는 것들이다. 대상 함수는 [decision.py:63 `compare_jeonse_wolse`](../../../src/onjeon/decision.py#L63).

> **실측 결과 (2026-07-27, Phase 1 구현 후 측정).** 기본 페르소나(월소득 280만·자산 2천만·27세·무주택·세대주)에 전세보증금 2억 / 월세 보증금 2천만·월 55만:
>
> | 케이스 | 전세 (전→후) | 월세 (전→후) | 결론 (전→후) |
> |---|---|---|---|
> | 중기업O · 4년 거주 | 296만 → **480만** | 388만 → **508만** | 전세(92만) → 전세(**28만**) |
> | 중기업O · 2년 거주 | 296만 → **480만** | 388만 → 388만 | 전세(92만) → **월세(92만)** |
> | 중기업X · 4년 거주 | 593만 → **566만** | 388만 → **508만** | 월세 → 월세(58만) |
> | 중기업O · 전세5천(한도내) | 116만 → **116만** | — | 불변 — 회귀 앵커 |
>
> **처음 예측보다 미묘했다.** 결함 A(한도)만 고치면 부호가 뒤집히지만, 결함 C(지원금 24개월)를 같이 고치면 월세도 비싸져서 4년 거주에서는 전세가 여전히 싸다 — 다만 마진이 92만 → **28만**으로 줄어 사실상 무차별에 가까워진다.
>
> 그래서 결함은 **개별로 고치면 안 된다.** 하나만 고치면 다른 방향 편향이 남아 결론이 오히려 더 틀릴 수 있다.
>
> 그리고 수정 후에야 **거주기간이 결론을 가른다**는 게 드러난다(2년→월세, 4년→전세). 수정 전에는 두 경우 다 "전세 유리"로 뭉개져 있었다. 화면에 거주기간 입력과 그 민감도를 노출할 근거다.
>
> 결함 F 수정은 전세를 **싸게** 만들었다(593만 → 566만) — 디딤돌 2.85%가 버팀목 2.7%로 교체되고 한도 2억이 대출 1.8억을 전부 덮기 때문이다. 편향의 방향을 미리 가정하지 말고 측정해야 한다는 사례다.

### 결함 F — 주택 구입자금 대출 금리가 전세보증금에 붙는다 (최고 심각도)

[decision.py:74](../../../src/onjeon/decision.py#L74)는 자격 있는 상품 중 `product_type == "loan"`이면 전부 후보로 넣고 `min(rates)`를 취한다. 그런데 `rules/products/`의 `didimdol-loan-2026-07`은 **내집마련 디딤돌대출 — 주택 구입자금**이다(`terms.note`: "LTV 70%. 주택 구입자금."). 전세자금 대출이 아니다.

실행으로 확인:

```
[중소기업 재직 O]  적용금리 1.20%  전세 296만  월세 388만  유리=전세   ← 중기청 1.2%가 가려준다
[중소기업 재직 X]  적용금리 2.85%  전세 593만  월세 388만  유리=월세   ← 디딤돌(주택구입) 2.85%가 붙는다
```

`didimdol`의 자격 조건은 `is_homeless`·`is_household_head`·`annual_income_krw`·`assets_krw` 4개뿐이라 기본 페르소나가 그냥 통과한다. 중기업 재직 체크만 끄면 **전세로 쓸 수 없는 상품의 금리로 전세 비용을 계산한다.** 결함 A(한도 누락)보다 심각하다 — 존재하지 않는 선택지를 근거로 결론을 내기 때문이다.

또한 `청년전용 버팀목전세자금대출`은 `interest_rate: null`(구간별 변동 `[확인]`)이라 후보에서 아예 탈락한다. 즉 **정작 전세 상품은 빠지고 매수 상품이 들어가 있다.**

→ 수정: 룰에 `applies_to: ["jeonse"] / ["wolse"] / ["buy"]`를 넣고 용도별로 필터. 결함 B와 같은 필드로 함께 해결된다. 버팀목 금리는 대표값 + `[확인]` 마커로 채운다(null이면 비교에서 조용히 사라지므로).

### 결함 A — 정책대출 한도 미적용 (전세를 실제보다 싸게 만든다)

```python
jz_rate = min(rates) if rates else market_params["loan_rate_jeonse"]
jz_cost = engine.annual_cost_jeonse(deposit=jeonse["deposit_krw"], loan_rate=jz_rate, ...)
```

자격 있는 상품의 **최저금리를 대출 전액에** 적용하는데, [engine.split_funding](../../../src/onjeon/l3/engine.py#L10)은 자금을 (자기자본, 대출) 2분할만 한다. 한도가 어디에도 들어가지 않는다.

예: 전세보증금 2억 · 자산 2천만 → 대출 1.8억. 중기청 전월세보증금대출은 금리 1.2%, **한도 1억**(`terms.limit_krw`). 현재 코드는 1.8억 전액에 1.2%를 매긴다. 실제로는 1억만 1.2%, 초과 8천만은 시장금리 3.5%다.

> 오차 = 8,000만 × (3.5% − 1.2%) = **연 184만원**

헤드라인 결론을 뒤집을 수 있는 크기다. 이 결함 하나만으로도 승격 전 수정이 필수다.

### 결함 B — 월세 쪽 대출 혜택 누락 (같은 방향으로 편향)

전세는 "자격 있는 최저금리"를 받는데 월세 보증금은 항상 `market_params["loan_rate_jeonse"]` = 3.5%다 ([decision.py:88](../../../src/onjeon/decision.py#L88)). 그런데 중기청 상품의 정식 명칭은 **"중소기업취업청년 전월세보증금대출"** — 월세 보증금에도 적용된다. 현재 `rules/products/` 5개 룰에 `applies_to` 구분이 없어 코드가 전세에만 쓰고 있다.

결함 A와 B가 같은 방향(전세 유리)으로 작용한다. 두 개를 함께 고쳐야 편향이 상쇄되지 않고 각각 정확해진다.

### 결함 C — 청년월세지원 240만원 하드코딩 (CLAUDE.md 원칙 3 위반)

```python

support = 2_400_000 if has_support else 0
```

`rule_id` 문자열과 금액이 코드에 박혀 있다. "룰은 코드가 아니라 데이터" 원칙 위반이고, 버전이 `2026-08`로 바뀌면 조용히 0이 된다.

추가로 **코드와 룰이 실제로 불일치한다.** 룰의 `terms.note`는 "월 최대 20만원 × 최대 **24개월**(총 480만)"인데 코드는 `2_400_000`(20만 × **12개월**)이다. 그리고 한시 지원을 **매년 반복** 차감한다. `expected_stay_years` 기본값이 4년이므로 4년 거주 시 총 960만원을 차감하는데 실제 지원 상한은 480만원이다 — **2배 과대 계상.**

**결정 (2026-07-27):** 총지원액을 거주기간으로 나눠 연평균화한다. 4년 거주 → 연 120만원. 비교 대상인 전세 비용도 거주기간 연평균 기준이므로 잣대가 같아진다. 원래 조건(24개월 한시)과 환산값을 breakdown·근거 섹션에 둘 다 남긴다.

```
연평균 지원 = min(monthly_support_krw × support_months,
                 monthly_support_krw × expected_stay_years × 12) ÷ expected_stay_years
```

거주가 2년 이하면 상한이 걸리지 않아 연 240만 그대로 나온다(정상).

### 결함 H — E[Loss]의 시간 단위가 문서에 없다 (헤드라인 크기가 2배 갈린다)

`engine.expected_loss(p, lgd, deposit)`은 `P × LGD × 보증금`이고, `annual_cost_jeonse`는 이 값을 **연간** 비용에 그대로 더한다. 그런데 `P(사고)`가 *연간* 확률인지 *계약기간(2년) 전체* 확률인지 어디에도 안 적혀 있다.

[synth.py](../../../src/onjeon/l2/synth.py)를 읽어 근거를 찾았다. 절편 `-7.5`이 `HUG_BASE_ACCIDENT_RATE = 0.022` — HUG 전세보증금반환보증 **연간** 사고율 2.2%(2025-08) — 에 앵커돼 있다. 따라서 P는 연간 확률이고 **연비용에 그대로 더하는 현재 구현이 맞다.**

수정할 계산은 없다. 하지만 이게 문서에 없으면 다음 사람이 "2년 계약이니 ÷2 해야 하나?"에서 반드시 멈추고, 잘못 고치면 헤드라인이 2배 틀린다. 수식 자체는 맞고 **근거만 비어 있는** 상태다.

→ 수정: `expected_loss` 독스트링에 "P는 연간 사고확률(HUG 연 2.2% 앵커) → 반환값은 연간 기대손실" 명기. 근거 섹션에 "연 사고확률 4.2%"로 **연 단위를 표기**해 노출. 화면에 "2년 계약 기준"으로 오독될 문구를 쓰지 않는다.

## 3. E[Loss]를 실제로 켜는 방법

`E[Loss] = P(사고) × LGD × 보증금`
`LGD = 1 − max(시세 × 낙찰가율 − 선순위, 0) / 보증금`

| 입력 | 현재 | 조달 방법 | 비용 |
|---|---|---|---|
| 보증금 | 사용자 입력 | 있음 | — |
| 시세 `market_price` | 없음 | **캐시에 이미 있다** — `market_trends` 평당가 × (전용면적 ÷ 3.3058). 면적은 등기부에서 파싱됨 | 무료·추가 API 호출 없음 |
| 낙찰가율 | `rules/auction_rates_2026-07.json` | 있음 | — |
| 선순위(채권최고액) | **없음** — [parse.py](../../../src/onjeon/register/parse.py)는 주소·면적·용도만 추출 | §3.1 | 반나절 |
| P(사고) | `l2.RiskModel` (sklearn) | **배포 런타임에 sklearn·numpy 없음** → §3.2 | 6줄 |

### 3.1 선순위 채권최고액 — 수동 입력 먼저, 파싱은 편의 기능

등기부 을구 텍스트 형식은 변동이 크고 OCR 신뢰도도 낮다. regex 파싱을 전제로 깔면 Phase 3가 파서 품질에 인질로 잡힌다.

**lazy 순서:**
1. 입력 폼에 `선순위 채권최고액` 필드 한 개 추가 (등기부 을구에서 눈으로 보고 입력) → 이것만으로 E[Loss]가 동작한다
2. `parse.py`에 regex(`근저당권` + `채권최고액\s*금?\s*([\d,]+)\s*원`) 추가 → **필드 자동채움**. 실패하면 빈칸이고 사용자가 채운다. 이미 있는 확인 게이트(`pendingReg`)가 검증을 담당한다

이러면 파싱 실패가 기능 실패가 아니다.

### 3.2 P(사고) — 계수를 룰 데이터로, 런타임은 stdlib

`requirements-api.txt`에는 numpy·pandas·scikit-learn이 없다 (커밋 `7485de9`가 의존성 11배 축소하며 제외). [model.py](../../../src/onjeon/l2/model.py)는 이 셋을 모듈 최상단에서 import하므로 컨테이너 배포 경로에서 **import 자체가 실패**한다.

sklearn을 다시 넣으면 그 커밋을 되돌리는 것(~150MB). 필요 없다. 로지스틱 회귀의 **추론**은 `1/(1+exp(-(b₀+Σbᵢxᵢ)))` 한 줄이고, `RiskModel`은 이미 순수 dataclass(coef·intercept·feature_means)다. numpy를 쓰는 유일한 지점이 `np.exp` 스칼라 호출이다.

**최소 diff:**
- `model.py`: `numpy`/`pandas`/`sklearn` import를 `train()`·`XGBRiskModel` 내부로 이동, `np.exp` → `math.exp`. → `RiskModel`이 stdlib만으로 import 가능 (약 6줄)
- `rules/risk_model_2026-07.json`: 학습된 coef·intercept·feature_means·`data_note`를 버전 태그와 함께 덤프 (오프라인 스크립트 1개)
- 런타임은 이 JSON을 `rules_io.load_rules`로 읽어 `RiskModel(**d)` — 새 클래스 없음

부수 효과로 CLAUDE.md 원칙 3(룰은 데이터)을 만족하고 모델 버전이 재현 가능해진다. `explain()`은 이미 순수 파이썬 선형 분해라 그대로 쓴다.

### 3.3 입력이 없으면 0이 아니라 "미반영"이라고 말한다

채권최고액 미입력, 또는 시세가 캐시에 없으면 → `risk_adjusted: false` + 사유. 화면은 `⚠️ 미회수 위험 미반영` 배지와 "등기부 을구의 채권최고액을 넣으면 위험까지 반영합니다" CTA. **E[Loss]를 0으로 조용히 두고 숫자를 내지 않는다** (CLAUDE.md 원칙 5 · 허구 금지).
